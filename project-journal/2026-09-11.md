# Project Work Log — 2026-09-11

Today, I resumed the project from yesterday’s clean repository state and focused first on work that could be completed and verified entirely on the computer, since the NUCLEO-F446RE board and data cable were still unavailable. I created and committed the initial STM32CubeMX project shell for the NUCLEO-F446RE, fixed the STM32CubeF4 package at V1.28.3, and performed a limited static clock-configuration study toward the approved 180 MHz platform target, including HSE bypass at 8 MHz, 180 MHz SYSCLK/HCLK, APB1 at 45 MHz, APB2 at 90 MHz, Voltage Scale 1, Over-Drive enabled, and the corresponding Flash latency. I deliberately stopped before continuing into ADC, TIM, DMA, and other peripheral configuration, because without the physical board those steps would provide little additional evidence and could create unnecessary rework.

I then completed Operations Work Package P0-A1, whose goal was to establish a reproducible computer-side development environment. I audited the repository and existing tools, normalized machine-specific absolute paths out of tracked documentation, verified the existing ARM C/C++ compiler and GDB, installed STM32CubeProgrammer 2.23.0, and confirmed that its command-line interface could be invoked successfully. I also created a repository-local `tools/environment-smoke.ps1` check that verifies Git, uv, Python 3.12.13, locked/offline Python environment synchronization, CMake, Ninja, ARM GCC/G++/GDB, STM32CubeMX command-line startup, STM32CubeProgrammer CLI operation, and an actual Cortex-M4F cross-compilation with the expected v7E-M, VFPv4-D16, and hard-float attributes. During this process, I debugged two environment-script issues: an initial PowerShell here-string construction error and a Windows PowerShell 5.1 behavior that treated a non-fatal CubeMX Java stderr warning as a terminating error. After isolating the latter with a dedicated process-level diagnostic and confirming that CubeMX exited with code 0, I revised the smoke script to capture stdout and stderr separately and judge success by the actual process exit code. The final repository-local smoke check passed completely, including Git hygiene checks for ignored virtual environments and build products, absence of tracked generated junk, and absence of machine-specific Windows absolute paths in tracked text. I documented the verified environment in `docs/environment.md`, updated the bring-up record, committed the completed P0-A1 package as commit `6337c44`, and pushed it to GitHub.

After P0-A1 passed, I moved on to Operations Work Package P0-A2, whose goal was to prove that the minimal CubeMX firmware shell could complete a real clean configure, compile, and link using the repository and the selected ARM GCC toolchain. I first isolated the earlier 180 MHz CubeMX experiment in a Git stash so that the firmware-build baseline would start from the committed minimal `.ioc` configuration rather than mixing unrelated clock changes into the milestone. I then generated the full CubeMX CMake project, including startup code, linker script, HAL/CMSIS sources, and CMake toolchain files, and performed a clean build from an empty `build/p0-a2` directory. The build successfully produced a real STM32 target ELF and linker map. I verified from both the ELF metadata and the actual compile database that the target was ARMv7E-M / Cortex-M4 with FPv4-SP-D16 and hard-float ABI, using `-mcpu=cortex-m4`, `-mfpu=fpv4-sp-d16`, and `-mfloat-abi=hard`. I then packaged the linked ELF into standard `.hex` and `.bin` images with `arm-none-eabi-objcopy`, producing `cubemx.elf`, `cubemx.map`, `cubemx.hex`, and `cubemx.bin`, and confirmed a firmware size of 7220 bytes of text, 20 bytes of data, and 1572 bytes of BSS. I also confirmed that build outputs remained ignored by Git, the `.ioc` file remained tracked, the generated source tree contained no machine-specific absolute Windows paths, and CubeMX’s `.mxproject` bookkeeping file was excluded from version control.

The P0-A2 baseline was documented in `docs/firmware-build.md` and committed as `337e6c8` (`build: establish reproducible firmware baseline`). The first push attempt failed because Git was trying to connect directly to GitHub while my browser was using a local VPN proxy. I diagnosed this by comparing the Windows user proxy, WinHTTP settings, environment variables, Git proxy configuration, TCP connectivity, and `curl` behavior. The system proxy was `127.0.0.1:7890`, while Git had no proxy configured. I therefore configured that proxy only for the current repository, verified remote access through it, and successfully pushed commit `337e6c8` to GitHub. At the end of the day, both P0-A1 and P0-A2 were closed as PASS. The computer-side environment and firmware build baseline are now reproducible and documented, while all board-dependent activities—ST-LINK connection, flashing, target boot, on-board debugging, VCP, real clock verification, ADC/TIM/DMA behavior, FreeRTOS runtime behavior, and all hardware validation gates—remain explicitly untested until the physical board and data cable are available.
