# Project Journal — 2026-09-13

Today was the first real hardware session after receiving the NUCLEO-F446RE board and a USB data cable.

Before today, the project had already completed P0-A1, the reproducible computer-side development environment, and P0-A2, the reproducible firmware build baseline. However, none of those results constituted real target-board validation. For that reason, I did not immediately move on to ADC, DMA, FreeRTOS application logic, or later risk gates. The goal of today's work was to complete P0-B and prove the minimum physical development loop step by step.

The first problem appeared almost immediately. The onboard ST-LINK could be enumerated successfully by STM32CubeProgrammer, and its serial number and firmware version could be read, but every attempt to connect to the STM32 target over SWD failed with:

`DEV_USB_COMM_ERR`

This was not treated as a random one-time failure. I reproduced the same behavior after a controlled USB reconnect, after changing to another physical USB port on the PC, and after changing to a second known-good USB data cable.

Windows still detected the expected ST-LINK/V2-1 USB functions, including ST-Link Debug, USB Mass Storage, the USB Composite Device, and the ST-Link Virtual COM Port. This helped separate USB enumeration from actual ST-LINK control and SWD communication.

The onboard ST-LINK firmware was initially:

`V2J28M18`

The Java-based ST-Link Upgrade 3.17.11 utility detected the probe but failed when attempting to enter update mode, reporting JNI/system error 121. No firmware was changed during that failed attempt.

I then used the official native Windows ST-LinkUpgrade utility from STSW-LINK007. The probe was successfully updated from:

`V2J28M18 → V2J48M35`

During the upgrade, LD1 flashed red repeatedly in a regular pattern.

After the firmware upgrade, SWD communication immediately worked. STM32CubeProgrammer identified the real target as:

- STM32F446xx
- Device ID: `0x421`
- Revision: Rev A
- Internal Flash: 512 KBytes
- CPU: Cortex-M4
- Target voltage: approximately 3.20 V
- SWD frequency: 4000 kHz

This was one of the most useful engineering lessons of the day: successful USB enumeration, successful ST-LINK communication, and successful target SWD connection are different layers and must be diagnosed separately. I avoided changing firmware application code, clock settings, or board jumpers while the actual failure was still in the debug-probe path.

Once the target connection was stable, I rebuilt the previously verified P0-A2 firmware baseline in a separate clean build directory. The tracked firmware source was confirmed to be identical to the P0-A2 milestone commit `337e6c8`.

The baseline build succeeded with:

- text: 7220 B
- data: 20 B
- bss: 1572 B

The first-flash ELF was:

`build/p0-b-baseline/cubemx.elf`

with SHA-256:

`09982EB00B2454C045B3A1DEFF2C34561A0CF018C77E0769DFFAB49B0F0437A7`

Before overwriting the target Flash for the first time, the existing MCU Flash contents were read back and preserved locally as ignored evidence. The project firmware was then programmed successfully, and Flash verification passed.

I kept the distinction between "flash succeeded" and "firmware executed" explicit.

For target execution and debugger proof, STM32CubeCLT 1.22.0 was installed only to obtain the official ST-LINK GDB server. I did not replace the existing Arm GNU Toolchain, CMake, Ninja, or CubeProgrammer setup, and I did not reinstall the ST-LINK driver.

The ST-LINK GDB server version used was:

`7.14.0`

Using the already-programmed ELF only for symbols, and without issuing a GDB `load` command, I completed the following sequence:

`reset → breakpoint at main() → continue → breakpoint hit`

The breakpoint was reached in `main()` at the `HAL_Init()` line. PC, SP, LR, and the backtrace were captured successfully.

This separately proved:

- target execution
- debugger connection
- reset
- hardware breakpoint
- continue-to-breakpoint behavior

The next step was the ST-LINK Virtual COM Port.

Before changing the firmware, I checked the existing CubeMX project. PA2 and PA3 were already assigned to USART2 TX/RX at the pin level, and Windows already exposed the ST-LINK Virtual COM Port as COM5, but the firmware did not yet contain a real USART2 HAL initialization path. This was a useful reminder that the existence of a COM port on the host does not prove MCU-to-PC serial communication.

USART2 was then formally enabled in CubeMX with:

- asynchronous mode
- PA2 = USART2_TX
- PA3 = USART2_RX
- 115200 baud
- 8 data bits
- no parity
- 1 stop bit
- TX/RX
- no hardware flow control
- oversampling 16

USART2 interrupts and DMA were intentionally left disabled.

After regeneration, I reviewed the CubeMX diff before building. No FreeRTOS, ADC1, TIM2, or DMA configuration was introduced. The newly added UART HAL/LL vendor files were SHA-256 checked against STM32CubeF4 V1.28.3 and matched exactly.

A deterministic startup banner was added only inside the CubeMX USER CODE region:

`P0-B VCP READY\r\n`

The implementation used a single blocking `HAL_UART_Transmit()` call during startup.

The VCP candidate was built in a new clean directory:

`build/p0-b-vcp-01`

The build succeeded with:

- text: 9620 B
- data: 40 B
- bss: 1640 B

The final VCP ELF had SHA-256:

`62AFAC04597BD590092042257D18C796E4DC9A3C1DDB0C3F88E7597FF6523BF2`

That image was flashed and verified successfully.

The host then opened the ST-LINK Virtual COM Port at 115200 8N1. I pressed the physical black RESET button twice in two separate trials. Both resets produced the exact expected message:

`P0-B VCP READY`

This completed the real host-to-board development loop:

`host build → ST-LINK/SWD → flash → execution → debugger → USART2/ST-LINK VCP → PC`
